## 怎麼提供第一批資料

1. 開啟網站，註冊並登入用戶帳號。
2. 對實際喜歡的飲料按收藏，對確實不喜歡的飲料按不喜歡。
3. 確認偏好已保存到帳號；訪客的 localStorage 收藏不會被雲端訓練取得，可使用頁面的匯入瀏覽器偏好功能。

不必為了湊數強行標註。不操作不等於不喜歡；真實、準確的訊號比資料數更重要。資料變多不保證每次更新都改善，需要持續比較驗證結果。

## 匯出與訓練

```sh
node scripts/export_preferences.mjs
.venv-training/bin/python scripts/train_preferences.py --snapshot internal_exports/匯出的檔名.json --epochs 10
```

第一行會列出實際匯出檔案位置；第二行將 `internal_exports/匯出的檔名.json` 替換成那個檔案。不要貼出快照內容。使用既有獨立訓練環境，安裝方式見 [本機驗證操作](RelGT本機訓練驗證操作.md)。

匯出使用唯讀 SQL，只查帳號 ID 與偏好欄位，不讀密碼、salt、session 或推薦原始文字。開發測試帳號排除；登入 ID 在本機以 HMAC 轉成穩定用戶代碼。HMAC key 與快照留在 `internal_exports/`，不提交 GitHub。

目前 Wrangler 遠端 D1 查詢回傳 7403 授權錯誤，儘管 `whoami` 顯示正確帳號與 D1 scope。這次改用已連接的 Cloudflare API 成功查到彙總，確認沒有真實資料，據此建立空快照。**CLI 雲端匯出尚未驗證成功，需要先恢復 D1 API 授權；不能把本次空快照當成未來雲端匯出已自動接好。** 可依 Wrangler 登入流程重新授權，之後再執行匯出。本機程式檢查與真實雲端訓練分開記錄。

## 模型怎麼學偏好

- 一筆標籤代表某用戶對某飲料的明確偏好：收藏為 1，不喜歡為 0。
- 未標註飲料不補成 0；不生成假用戶、假收藏或假不喜歡。
- 無效飲料 ID 移除；同一用戶重複操作去重；同時喜歡與不喜歡的衝突 ID 兩邊都移除並計數。
- 使用官方 RelGT 的完整 local/global 模型；每個樣本取飲料、用戶、品牌、茶種、奶類、配料 6 個具型別 token。時間為 0，因為目前快照沒有事件歷史。
- 用戶代碼作類別特徵，讓共用模型學習不同用戶的標籤；不同用戶不是各訓練一個完全獨立模型。
- 使用 Adam 與 BCEWithLogitsLoss，從頭初始化；這個入口沒有拿價格回歸權重假裝偏好 checkpoint，也還沒有續訓 CLI。
- 單筆資料也能執行。因官方 BatchNorm 與 readout 需要至少 2 個 batch 元素，內部重複同一筆真實樣本後只取一份 loss，不增加報告的樣本數。
- 只有正向或只有負向資料時仍可測試訓練，但不能宣稱已學到可靠的喜歡／不喜歡分界。

## 少量資料如何驗證

少於 30 個有效標籤，或任一類少於 3 筆時，全數用於訓練，報告標示 `trained_unvalidated`。這是「是否有足夠資料切驗證組」的規則，不是阻止訓練的門檻。

資料較多時，依用戶＋品牌＋去空白品名做固定約 80/10/10 分組；同名變體不跨組，特徵字典與統計只用訓練組。分組後仍太少則改回全數訓練，明確不報保留驗證品質。

目前只是快照分組，沒有真實互動時間，因此不是正式時間切分的推薦評估。報告列出 loss、分類 accuracy 與樣本數；accuracy 受類別比例影響，不能單獨當作推薦變好的證據。Recall@K／NDCG@K、排序基線比較與線上效果仍待加入。

## 每次輸出與限制

每次實際執行都輸出 `docs/training-runs/<run-id>.md`、JSON 及 `daily.txt` 摘要。報告只含彙總、參數與限制；沒有逐人喜歡清單。若執行訓練，權重與用戶特徵只存於忽略的 `training_artifacts/`；若資料為零，不生成 checkpoint。

這次新增的是可執行的偏好訓練入口，沒有將模型分數接入網站 B 榜單，沒有提供雲端發布或每日 04:00 排程，也沒有保證小資料一定勝過既有基線。後續仍需事件紀錄、正式排序評估、候選分數匯出、模型版本切換與續訓流程。
