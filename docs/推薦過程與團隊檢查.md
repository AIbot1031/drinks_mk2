# 推薦過程與團隊檢查

## 線上查看

團隊頁面：[推薦過程檢查](https://drinks-mk2.rtx941031.workers.dev/internal)。使用專案負責人提供的團隊 ID 與密碼登入。密碼已設定於 Cloudflare secret `REVIEW_KEY`，沒有放進 GitHub。負責人本機的 `.review-access.txt` 保存網址、ID 與密碼，此檔不提交。

登入有效 8 小時，使用簽章、HttpOnly、Secure、SameSite cookie。公開頁面只顯示登入表單；查詢紀錄、完整榜單與 JSON 都需要驗證。這是團隊共用 ID 與密碼版本，尚未提供個別成員帳號、分級權限或成員稽核。

每次有效推薦請求，包括被資料限制阻擋或沒有候選的結果，都先存入專案專用 Cloudflare D1 `drinks-mk2-traces`，再回傳給消費者。存檔失敗時回應錯誤，不悄悄略過。格式或大小無效的 API 請求會在輸入驗證階段拒絕，沒有推薦流程紀錄。

## 每一筆紀錄能看到什麼

| 區段 | 內容 |
| --- | --- |
| `input` | 中文需求、表單條件、收藏 ID、不喜歡 ID、換批排除 ID、推薦數量。 |
| `understanding` | Agent A 整理後的條件、偏好、提醒與是否阻擋。此版 parser 為 rules，大模型未使用。 |
| `filtering` | 原始筆數 → 硬篩選後 → 排除不喜歡後 → 排除已看過後。 |
| `config` | A/B 權重、RRF 常數、候選數、圖傳播次數、重啟比例、品牌限制。 |
| `routeA` | A 榜單前 100 名：原始餘弦分數、飲料 ID、名稱、品牌、Excel 來源列。 |
| `routeB` | B 榜單前 100 名：圖傳播分數、種子來源、種子飲料、來源列。此版尚非 RelGT。 |
| `fusion` | 候選聯集、A/B 名次、兩條路徑的個別貢獻、實際計算式、總分與融合名次。 |
| `selection` | 依品牌多樣性選取、延後、名稱去重及補足的每個決策；最後消費者名次與原融合名次。 |
| `consumerOutput` | 推薦 API 實際輸出的飲料與資料依據，尚未附加外層 `traceId`。 |
| `rendering` | 前端卡片使用哪些欄位。Agent C 未使用。 |

完整紀錄只保留真正進入融合的各路徑前 100 名，而非將 1,178 款飲料的每個向量全部保存。來源筆數與篩選統計會一併記錄。

## 權重如何計算

目前融合使用加權 Reciprocal Rank Fusion（RRF）：

```text
A 貢獻 = 0.65 / (60 + A 名次)
B 貢獻 = 0.35 / (60 + B 名次)
融合分數 = A 貢獻 + B 貢獻
```

某條路徑沒有該飲料時，該路徑貢獻為 0。A 的餘弦分數與 B 的圖傳播分數不直接相加，因為尺度不同。

例如某款飲料 A 第 1 名、B 第 3 名：

```text
A 貢獻 = 0.65 / 61 = 0.0106557377
B 貢獻 = 0.35 / 63 = 0.0055555556
總分 = 0.0162112933
```

以上是公式示例，不是宣稱某一飲料的實際名次。每筆真實紀錄的 `fusion.ranked[].calculation` 與個別貢獻可自行核對。這些權重是基線設計，尚未用使用者互動資料校準或訓練。

## 從融合榜到消費者畫面

1. 依融合分數由大到小排序，同分依穩定飲料 ID 排序。
2. 第一輪每個品牌優先最多 2 杯，以增加品牌多樣性。
3. 同一品牌、同一品項名稱只呈現一次。
4. 若推薦杯數不足，第二輪允許更多同品牌飲料補足，但仍不放寬預算、奶類或營養限制。
5. 以選取順序生成最終榜單。`originalFusionRank` 能看出是否因多樣性而調整。
6. 消費者卡片讀取名稱、品牌、價格原文、風味、熱量、咖啡因和固定規則依據，完整內部榜單不送到公開前端。

空白需求又沒有收藏時，沒有個人 B 圖種子，B 榜單可能是空的；不會憑空生成個人偏好。收藏存在時以收藏為種子，否則用查詢的前五個正分候選。

## 下載檔案

在線上檢查頁選擇一筆紀錄，再按「下載完整 JSON 檔」。也可在已登入 Cloudflare 的本機執行：

```bash
npm run trace:export
npm run trace:export -- 某筆紀錄的UUID
```

第一個指令匯出最近 20 筆，第二個指令匯出指定一筆。生成檔案在 `internal_exports/`，不提交 GitHub。本機資料庫可以加 `--local`。

不經網站，直接使用引擎產生範例：

```bash
npm run trace:sample -- 想喝清爽回甘的茶，預算60元
```

這份檔案是本機引擎計算，不會自動成為線上 D1 紀錄。可參考[完整範例 JSON](examples/recommendation-trace.json)。

## ID、密碼管理與資料維護

ID 至少 3 個字元，密碼至少 6 位，兩者只接受 ASCII 英文字母（大小寫）或數字，區分大小寫，最多 200 個字元。中文、空白與符號都不接受。表單與 API 皆驗證；格式錯誤回傳 400，正確格式但憑證不符回傳 401。目前團隊 ID 為 `team001`，由 wrangler.jsonc 的 REVIEW_ID 設定；密碼仍保存在 secret。修改 ID 後需重新部署。

檢查密碼只分享給團隊成員。需要更新時由負責人在終端機執行 `npx wrangler secret put REVIEW_KEY`，在互動提示中輸入新值；新值會讓先前簽章 cookie 失效。不要把密碼貼進 GitHub 或公開網址。更新後本機 `.dev.vars` 與 `.review-access.txt` 也需同步保存。

紀錄保存於 D1，目前不會自動刪除。可在 Cloudflare D1 面板查看大小與查詢；本版沒有公開刪除 API。請依實際使用量制定保存政策。紀錄不額外收集 IP、帳號或瀏覽器指紋；使用者輸入、偏好 ID 與推薦資料包含在內部紀錄中。

[Cloudflare D1 binding 官方文件](https://developers.cloudflare.com/d1/worker-api/d1-database/)說明資料庫與 Worker 的連接；[Workers secrets](https://developers.cloudflare.com/workers/configuration/secrets/)說明密碼保存。
