# RelGT 訓練設計與更新報告

更新日期：2026-10-10（台灣時間）

**本文件是正式用戶推薦訓練的設計與每次報告規格。已完成一次官方 RelGT 的飲料價格回歸驗證，但尚未訓練正式用戶偏好模型，不能把下列計畫視為已完成的推薦實驗。**

## 已確認的目標

- 訓練機器：目前連接的 Mac mini，Apple M6，32 GB。
- 排程：每天 Asia/Taipei 04:00 開始，執行至訓練與驗證完成，不設定固定截止時間。
- 雲端：網站與用戶事件由 Cloudflare 提供；Mac 負責訓練。
- 模型：初期採共用 RelGT，依各用戶互動產生個人化 B 榜單。
- 發布：只有通過驗證的新版本才能切換；保留前一版本，不發布半完成結果。
- 每次訓練都要記錄報告，並將安全的摘要追加到根目錄 daily.txt。

## 預定如何訓練

1. **收集事件**：新增穩定用戶代碼、飲料 ID、事件類型及時間。收藏、取消收藏、不喜歡、評分要有各自的事件，不只保存目前清單。訓練匯出不包含密碼、session 或不必要的個資；排除開發測試帳號。
2. **固定資料快照**：每次訓練記錄資料截止時間、來源版本與匯出水位。新事件留到下一次訓練，避免同一次實驗讀到不一致資料。記錄去重、無效 ID 與被排除資料數。
3. **建立關聯表與圖**：整理用戶、飲料、品牌、茶種、奶類、配料與互動事件，對應官方 RelGT 的異質／時間圖輸入。ID 對照、特徵編碼與模型檔案要一起版本化。
4. **定義推薦任務**：設計用戶與飲料的偏好預測任務。明確不喜歡可提供負向訊號；沒有收藏不能直接當成不喜歡。標籤權重、負樣本與損失函數仍待小型實驗確認，不宣稱原官方程式已直接支援本專案推薦任務。
5. **時間切分**：依事件時間分訓練、驗證與測試，確保未來事件不洩漏到過去的圖、標籤或特徵。固定評估方法後才比較新舊版本。
6. **初次訓練與後續更新**：第一次建立可驗證模型；之後可載入上一版 checkpoint，以新資料加歷史資料微調，避免只學最新一天。保存模型、優化器、進度、隨機種子、資料版本與設定，以便續訓及追查。是否定期從頭重訓待評估。
7. **驗證**：預計比較 Recall@K、NDCG@K、品牌／品項覆蓋及基線結果；K、樣本門檻與發布判準待資料量足夠後定義。沒有有效驗證資料時，不以低訓練 loss 宣稱推薦品質改善。
8. **匯出個人化結果**：用戶候選 ID、分數、模型版本與資料截止時間一起匯出。新用戶或資料不足時沿用基礎推薦。新收藏在下次模型更新前仍可供現有特徵圖使用。
9. **發布**：先上傳候選版本、確認檔案及用戶 ID 對照，再切換目前版本。雲端仍會做品牌排除、預算等硬篩選，再與 A 榜單融合。上傳模型權重本身不會自動完成網站推論。
10. **報告**：成功、失敗、資料不足而略過、前次未完成而略過，都要留下真實紀錄。Mac 關機而沒有執行的時段，只有後續偵測到漏跑才能寫入，不虛構當時執行紀錄。

## 每次訓練更新報告格式

每次執行使用唯一 run ID。預計本機保存 Markdown 人類可讀報告及 JSON 結構化紀錄；目錄驗證入口已自動生成本機報告；雲端保存與團隊頁查看仍待接上正式訓練流程。

| 區段 | 必須記錄 |
| --- | --- |
| 執行資訊 | run ID、時區、開始／結束時間、耗時、成功／失敗／略過、觸發方式。 |
| 程式與環境 | Git commit、模型設定版本、晶片、記憶體、CPU／MPS、相依套件版本。 |
| 資料 | 截止時間、快照版本、新增／總事件數、用戶數、飲料數、去重與排除筆數、各時間切分筆數。 |
| 實際處理 | 本次新增或修改了哪些表、特徵、標籤、樣本規則；未改動也明確寫出。 |
| 訓練方式 | 初次訓練／從頭重訓／微調，起始 checkpoint、參數、epoch／步數、學習率、batch、隨機種子。 |
| 訓練結果 | 真實 loss 與評估指標、有效樣本量、新舊版本比較、記憶體與執行時間、已知限制。 |
| 發布結果 | 是否通過判準、是否上傳／啟用、新舊模型版本、更新的用戶數、檔案校驗及失敗時沿用版本。 |
| 變更說明 | 「這次更新了什麼」「為什麼改」「驗證得到什麼」「用戶會受到什麼影響」。 |
| 錯誤與下一步 | 失敗階段、經過遮蔽的錯誤摘要、可恢復 checkpoint、下一次需要處理的事。 |
